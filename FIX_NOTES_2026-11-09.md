# ScholarshipHive — Combined fixes (9 November 2026)

This is a full-source ZIP based on `ScholarshipHive_Web_Visitor_Validation_Password_UI_Fix_2026-11-06.zip`.
The earlier file structure and packaged SQLite development database were retained.

## Requested changes

1. Login screen wording: `Apply for Leave` and `Request For Custom Shift` (no changes to their actions or connectivity requirements).
2. Web Add User: removed the manually coded password Show/Hide button. The existing site-wide toggle creates one consistent toggle. Removed duplicate toggle from the department-head Add Employee form as well.
3. Web Add/Edit User: Department selection now appears only when Role is Employee. Role-based department restrictions are still checked on the server.
4. Mobile self-registration: Shift/Department dropdowns use expanded layouts; long shift labels truncate gracefully on narrow devices instead of overflowing.
5. Department head / web API 401: signed-in department heads may open the read-only `api/team-scope` endpoints with a web cookie; normal browser navigation redirects to the actual `/TeamScope` web portal. API mutations still require a **separately validated JWT** (preventing CSRF via cookie-only access); web employee creation continues through the existing anti-forgery-protected `/TeamScope/Add` form. Scope checks still limit each head to their own department.
6. Announcement author on edit: original `AuthorId` remains unchanged for ownership/audit, and optional `LastEditedByUserId` records the latest editor. Mobile/API/UI now show the latest editor as the visible message source, with original publisher also visible on the web. The same behavior applies to both web and mobile edits.
7. Announcement visibility: department heads cannot continue seeing a notice only because they originally wrote it, after an owner moves it to another department. Only the appropriate recipients/admins see it. Creator edits are also restricted to the creator's audience scope.
8. Announcement changes now add an explicit `Edited` audit record containing the editor's username, announcement ID and old/new audience; general audit logs include changed property names, **not private field contents**. The editor action and announcement are saved within one database transaction. The audit screen has a Details column and `Edited` filter.
9. Announcement reassignment sends FCM notification to its newly targeted audience when FCM is configured. The login popup and history will read the new editor via API regardless of FCM configuration.
10. Department-head/reception notification bell now opens their appropriately scoped Announcements view instead of the global Pending Approvals page (which denied them with 403). Direct `/Notifications` visits redirect too; no global approvals are exposed to a head.
11. Local 4 GB laptop: retain the low-RAM Gradle configuration that successfully built the APK on 9 November. Flutter version/dependency versions were not upgraded.

## Data and migrations

- SQLite development: idempotent `ALTER TABLE` checks on startup add `Announcements.LastEditedByUserId` and `AuditEvents.Details` to existing databases without replacing data.
- PostgreSQL: migration `20261109000100_AddAnnouncementEditor` adds these two nullable columns, the optional editor FK and index.
- Historical audit records that were never written cannot be reconstructed; **test with a new edit after running this release**.
- This ZIP retains the original packaged `ScholarshipHive.dev.db`, but it is only the database from the uploaded ZIP. **If the active laptop has newer users or attendance data, back up its current `ScholarshipHive.dev.db` and copy it into the newly extracted project before starting the backend.** Do not extract over an active project/DB without a backup.

## Run / test — Windows PowerShell

Stop old backend (`Ctrl+C`) and old Flutter debugging session (`q`) first. Extract the ZIP to a separate folder, then update the path below if required.

**Backend (PowerShell 1):**

```powershell
cd "C:\Users\assam\Downloads\ScholarshipHive\backend\ScholarshipHive.Server"
dotnet restore
dotnet build
if ($LASTEXITCODE -eq 0) { dotnet run }
```

**Separate Razor web portal:** open `http://localhost:5080` in Chrome. Do NOT run Flutter Chrome to get the Razor admin/head portal. Test Add User, Head of Processing dashboard, bell, announcements and Auditor > Audit Activity.

**Mobile (PowerShell 2):**

```powershell
cd "C:\Users\assam\Downloads\ScholarshipHive\mobile"
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
```

If the phone ID changes, replace `895bd8c3` with the new ID from `adb devices -l`.

## Acceptance checklist

- Add User on web: one password toggle; selecting Auditor/Head/Admin-type roles hides Department; Employee shows it.
- Register on a narrow phone: Day/Night/Internship shift list is usable without RenderFlex overflow.
- Web Head of Processing: create employee via `/TeamScope` with no 401 and see only Processing people; try `/api/team-scope/employees` in a logged-in browser to be redirected to `/TeamScope`. Mobile API still works with JWT.
- Publish a Processing notice as Head of Processing, then edit it as Admin and reassign it to Calling. Calling employee sees latest text attributed to Admin; head no longer sees other-department content. The original creator remains preserved in the record.
- Log in as Auditor; `/ActivityLog` displays an `Edited` event for that announcement with old/new audience. Earlier unrecorded activity remains unavailable.
- Head clicks bell: scoped Announcements, not a 403; global approvals are not exposed.
- Regression check: login, office Wi-Fi check-in/out, attendance reports, leave and shift requests, reception, admin portal and Android app.

## Verification limitations

The package passed file integrity, source consistency, and local SQLite schema-upgrade smoke checks in the authoring environment. **A real `dotnet build`, Flutter compile, live authentication tests, and Android/browser UI regression tests were not executable in that environment**; they must be checked on a Windows machine with the relevant SDKs, local database, and test accounts. No claim of zero remaining bugs is made.
